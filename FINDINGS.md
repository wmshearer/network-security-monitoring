# Findings: detection scoring against ATT&CK ground truth

Raw scoring JSON: `evidence/scoring_results.json` (generated by
`src/score_detections.py`; see that script's module docstring for the full
scoring-unit methodology this document summarizes).

## Scoring unit

These are SPL detection rules, not a per-event classifier. Scoring uses two
deliberately different units, reported side by side rather than collapsed
into one manufactured ratio:

- **TP / FN -- capture level.** Each of the 5 atomic OTRF captures is one
  execution of one ATT&CK technique (ground truth from that capture's own
  metadata YAML). A detection is a TP against a capture if it matches at
  least one event in that capture; FN if it matches zero. D6 targets 3
  captures (cross-cutting parent-child heuristic, not technique-specific),
  so it has 3 TP/FN opportunities instead of 1.
- **FP -- event level**, against the 242,133-event benign baseline. Reported
  as a raw count of matching benign events, not a rate -- a rate against
  242,133 would overstate confidence from a small, non-representative
  sample (see caveats below).

## Read this as "clean on this data," not "production-ready"

100% recall / 0 FP on 8/8 opportunities is a small, curated sample, and
every detection was fit to the exact command lines and event fields present
in these 5 specific captures -- a methodologically honest way to build a
first detection pass against known telemetry, but also exactly the setup
where overfitting to the sample is easiest to miss:

- D2 keys on the literal words `powershell` and `hidden` appearing together
  in a `schtasks.exe` command line. A payload using `-windowstyle hidden`
  instead of `-W hidden`/`hidden`, or omitting the word "powershell" from a
  fully-pathed non-obvious binary, would not match.
- D3/D4 key on the literal `net.exe`/`net1.exe` binary path plus a
  `localgroup`/`user` keyword. A renamed binary, a non-standard invocation
  path, or native PowerShell cmdlets doing the same enumeration
  (`Get-LocalGroupMember`, `[ADSI]` bindings) instead of shelling out, would
  not match.
- D5's AUDIODG.EXE-targeting heuristic is specific to this Metasploit
  module's implementation (it goes through the Windows Audio Device Graph
  process). A different mic-access technique that doesn't touch AUDIODG.EXE
  would not match.
- D1 is the most durable of the six: it keys on a real Windows API-level
  fact (a named value written under a `Run` key) rather than a specific
  tool's command-line syntax, so it should generalize better to other
  Run-key-persistence tooling than D2-D5 generalize to other tooling for
  their techniques. Stated as a hypothesis -- not tested here against other
  tools' Run-key persistence.
- D6 is the one detection here that is intentionally not
  technique/tool-specific (parent-child relationship, not command-line
  content) -- the closest of the six to "would probably still catch a
  different PowerShell-launched net.exe/schtasks.exe invocation," though it
  would still miss a payload that avoids spawning those two specific child
  binaries.

## The one real false-positive-avoidance finding worth publishing

D1's condition specifically requires **EventID 13 (SetValue)** on a **named
value** under `...\Run\...` (e.g. `...\Run\Updater`) -- not just "any event
touching a Run key." This distinction was found by looking at the data, not
assumed up front:

The benign baseline has **11 legitimate EventID 12 (CreateKey) events**
creating the Run key itself (`HKLM\...\CurrentVersion\Run`,
`HKU\...\CurrentVersion\RunNotification`) via `sihost.exe` (normal Windows
shell-infrastructure process initializing its own registry hierarchy, not
persistence). A naive detection matching "any Sysmon event where
TargetObject contains Run" would have fired 11 times on entirely benign OS
behavior. Requiring EventID=13 (value write) plus a value-name segment
after `\Run\` eliminates all 11 without weakening the real detection -- the
benign baseline has zero EventID=13 SetValue events anywhere under a Run
key (confirmed directly during detection development, not assumed).

This near-miss false positive did not make it into the final detection
(D1 as shipped has 0 FPs) precisely because it was found and fixed during
development -- reported here per the task's "report bad numbers, don't hide
them" instruction, even though the shipped version is clean.

## What the FP count does and does not mean

Zero benign FPs across all 6 detections is a real, verified result on this
specific 242,133-event baseline -- but that baseline is one fairly idle
Windows Server 2022 host over a short capture window, not a busy production
domain controller or a fleet of workstations running IT management tooling.
This baseline likely UNDERSTATES real-world FP risk for at least:

- D3/D4 (net.exe enumeration): legitimate sysadmin/helpdesk scripts,
  monitoring agents, and some commercial EDR/inventory tools shell out to
  `net.exe user`/`net.exe localgroup administrators` routinely on a managed
  fleet. This baseline simply never happened to run such tooling during its
  capture window -- an absence of opportunity, not evidence the behavior is
  rare in general.
- D6 (PowerShell spawning net.exe/schtasks.exe): common in real
  administrative automation (deployment scripts, PowerShell-based logon
  scripts that call out to `net.exe`).

D1 and D5 are the two detections with higher confidence of generalizing
past this specific baseline's quietness, because their signal is closer to
the OS/API level (a specific EventID+registry-path combination; a specific
process-access target) than to "did IT tooling happen to run during the
capture window."

## Ground truth caveats

- Ground truth is capture-level, not event-level (see README.md's "What
  'attack' labels actually claim"). A TP means "the detection fired
  somewhere inside the capture that IS this technique," not "the detection
  fired on the single event that best represents the technique" -- though in
  practice, for D1-D5, the matching events ARE the technique-defining action
  itself (verified by inspecting the actual matched events in
  `evidence/detection_dev/`, not assumed).
- APT29 compound captures (Day1/Day2, ~783K events) are excluded entirely --
  no per-technique ground truth exists for them anywhere in this dataset
  (see README.md). They were not scored, not sampled, not spot-checked
  against these detections. This is a real, stated gap: if any of these 6
  detections would fire (correctly or as a false positive) inside the APT29
  telemetry, this project does not know and does not claim to know.

## Alert-firing evidence (trial-window-critical deliverable)

All 6 saved searches are scheduled (`enableSched=1`, `logevent` alert
action) and were observed firing on their real cron schedule (not just
manually dispatched via REST `/dispatch`, which was tried first and does
NOT invoke alert actions -- only the actual scheduler does):

- `evidence/fired_alerts_snapshot_1.json` -- `alerts/fired_alerts` REST
  snapshot showing `triggered_alert_count=1` for D1-D5 after their first
  scheduled run.
- `evidence/splunkd_log_alert_fires.txt` -- `splunkd.log` excerpt showing
  `sendmodalert`/`logevent` invocations completing with `exit code=0` for
  D1, D2, D3, D6 at their `08:45:00` scheduled run. An earlier attempt at
  `08:40:00` failed with `HTTP Error 400` -- see README.md's "What broke"
  section for the missing-required-`action.logevent.param.event` bug this
  caught and fixed before the next scheduled run.
- `evidence/detection_lab_alerts_index_contents.json` -- the actual indexed
  `logevent` output in the dedicated `detection_lab_alerts` index, showing
  `detection=<name> technique=<id> result_count=<N>` for each fire, with
  `result_count` matching this document's TP counts exactly (D1=2, D2=1,
  D3=2, D6=3).
